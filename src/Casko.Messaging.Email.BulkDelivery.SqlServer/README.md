# SQL Server notification provider

Register with `services.AddSqlServerNotifications(connectionString)`. The API binds `Notifications:Ingestion` to the shared options. EF context, entities and migration names retain their original namespaces so relocating the assembly preserves migration identity and snapshot entity names.

## Bulk ingestion

Each attempt opens its own connection/transaction, streams rows through two SqlBulkCopy operations into temporary tables, then inserts missing events and deliveries using set-based SQL. BatchSize=1000 controls transport chunks, not commits. IDs are resolved by event key, not OUTPUT ordering. Identity and rowversion values are generated by SQL Server.

Temporary columns inherit the destination column collations using SELECT INTO. Key equality follows the existing database columns (commonly case-insensitive, including SQL trailing-space comparison behavior). Message/EventType/Template conflict comparison is byte-exact after serializing the shared message record. A future provider must explicitly match these identity semantics or provide a data migration.

UPDLOCK/HOLDLOCK protects checks against concurrent writers; existing unique indexes remain the final constraints. Deadlock victims retry the whole operation at most twice after the first attempt. Cancellation rolls back; database failures are not converted into success. No delivery is claimable before commit.

Queue claims retain the existing atomic UPDATE/OUTPUT and live-lease checks. The SQL-specific RowVersion is not part of shared contracts.

## Priority and lanes

The priority claim order is Critical, Normal, then Bulk; each priority remains FIFO by CreatedUtc and ID. The claim query uses the `IX_NotificationDeliveries_Status_Priority_CreatedUtc_Id` index introduced by the priority migration. Bulk rows age into Normal ordering after the configured `BulkPromotionAfter` interval, so a continuous normal workload cannot starve old campaigns.

The worker uses two independent lanes: the critical lane claims only Critical deliveries, while the standard lane claims Bulk through Normal. `CriticalConcurrency` and `CriticalMaximumMessagesPerSecond` reserve SMTP capacity for the critical lane. The default lane limits are both one message per second, so the configured SMTP service must permit their combined maximum of two messages per second. Set the two limits to stay below the provider's aggregate limit.

## Migrations and verification

Existing migration ID: `20260904200400_InitialNotifications`. Tables, keys, column types and status values are unchanged. The provider initializer applies only pending migrations.

Set `CASKO_TEST_SQL` to a test SQL Server connection with CREATE DATABASE permission, then run:

```sh
dotnet test tests/Casko.Messaging.Email.Tests
```

Tests create and drop uniquely named databases; they do not operate on the connection string's application database. Without the variable SQL tests are explicitly skipped. The shared contract test base can be reused with another provider fixture.

For the opt-in comparison benchmark:

```sh
CASKO_RUN_BENCHMARKS=1 dotnet test tests/Casko.Messaging.Email.Tests --filter FullyQualifiedName~Benchmark_creation --logger 'console;verbosity=detailed'
```

This compares the former sequential EF event/recipient creation, EF recipient batches of 1000, bulk distinct events, and bulk recipients at 1000 and 10000 deliveries. It reports elapsed time, throughput, process allocations, and SqlClient diagnostic command counts. Bulk-copy streams are reported separately from SQL commands; numbers are environment-specific, not production capacity guarantees.

The meter `Casko.Messaging.Notifications` exposes ingestion duration, inserted/reused event/delivery counts, deadlock retries and failures. Subscribe to it from your telemetry collector. Structured commit logs contain counts and duration only, not recipient addresses or message content.

## Local benchmark results

Measured on 2026-09-05 with .NET 10.0.11 and Azure SQL Edge in a disposable local Podman container (same engine image as the current AppHost). Single measured pass, Debug build, no separate warm-up. Allocation is cumulative managed process allocation, not peak memory. These results demonstrate the batching effect; production sizing needs measurements on the target SQL Server deployment.
